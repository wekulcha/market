# KULCHA Features README — требования к функциональности

Документ можно использовать как основу для раздела ВКР **"Формирование требований к программной системе"**. Здесь под требованиями понимаются функциональные возможности, которые должны быть доступны разным ролям системы: клиенту, администратору ресторана и суперадминистратору платформы.

## 1. Назначение функциональных требований

Система KULCHA предназначена для цифровизации приема, обработки и контроля заказов в кафе и небольших ресторанах через Telegram Mini App, веб-панели и Telegram-ботов.

Функциональные требования описывают:

1. какие действия пользователь может выполнить в системе;
2. какие данные он видит и изменяет;
3. какие ограничения доступа применяются для разных ролей;
4. какие дополнительные функции нужны для повышения удобства, надежности и управляемости платформы.

## 2. Основные роли системы

| Роль | Назначение |
|---|---|
| Клиент / пользователь | Оформляет заказ, выбирает ресторан и блюда, отслеживает статус заказа |
| Администратор ресторана | Управляет заказами, меню, сотрудниками, настройками ресторана и аналитикой |
| Суперадминистратор | Управляет всей платформой: ресторанами, пользователями, заказами и техническим состоянием |
| Курьер | Получает заказы на доставку и видит историю доставок |
| Оператор поддержки | Обрабатывает обращения пользователей через support-бота |

Ключевые роли для дипломного описания: **клиент**, **администратор ресторана**, **суперадминистратор**.

## 3. Функциональность клиентской стороны

Клиентский контур представлен Telegram Mini App (`user_panel`) и пользовательским ботом (`user_bot`).

### 3.1 Регистрация и авторизация

Клиент должен иметь возможность:

- открыть Mini App из Telegram;
- пройти авторизацию через Telegram WebApp flow;
- зарегистрироваться через бота, отправив контактный номер телефона;
- автоматически использовать Telegram ID и username для идентификации в системе.

Смысл функции: клиент не устанавливает отдельное мобильное приложение, а входит через привычную Telegram-среду.

### 3.2 Просмотр ресторанов

Клиент должен иметь возможность:

- увидеть список доступных ресторанов;
- открыть карточку выбранного ресторана;
- увидеть название, адрес, обложку и доступность ресторана;
- перейти к меню выбранного ресторана.

Смысл функции: пользователь быстро выбирает точку питания, из которой хочет сделать заказ.

### 3.3 Просмотр меню и блюд

Клиент должен иметь возможность:

- просматривать список блюд выбранного ресторана;
- видеть название, описание, цену, категорию, вес, калорийность и изображение блюда;
- фильтровать или визуально ориентироваться по категориям меню;
- открывать подробную карточку блюда;
- добавлять блюдо в корзину.

Смысл функции: меню заменяет бумажный каталог и дает клиенту актуальную информацию о доступных позициях.

### 3.4 Корзина

Клиент должен иметь возможность:

- видеть добавленные блюда;
- изменять количество позиций;
- удалять позиции из корзины;
- видеть итоговую стоимость;
- перейти к оформлению заказа.

Смысл функции: корзина позволяет проверить состав заказа до отправки в ресторан.

### 3.5 Оформление заказа

Клиент должен иметь возможность:

- выбрать тип заказа: доставка или заказ в зале;
- для доставки указать локацию внутри рынка: этаж, линию, павильон;
- для заказа в зале указать номер стола;
- указать или подтвердить номер телефона;
- добавить комментарий к заказу;
- выбрать способ оплаты;
- отправить заказ в ресторан.

Система должна проверять:

- что пользователь зарегистрирован;
- что корзина не пуста;
- что ресторан выбран;
- что для доставки указан адрес;
- что для заказа в зале указан номер стола;
- что заказ создается в допустимое время приема заказов.

Смысл функции: система собирает все данные, необходимые ресторану для приготовления и передачи заказа.

### 3.6 Профиль пользователя

Клиент должен иметь возможность:

- просматривать Telegram ID, username и телефон;
- сохранять типовую локацию на рынке;
- повторно использовать сохраненный адрес при следующих заказах.

Смысл функции: повторные заказы становятся быстрее, так как клиент не вводит одни и те же данные каждый раз.

### 3.7 История и статусы заказов

Клиент должен иметь возможность:

- видеть активные заказы;
- просматривать историю заказов;
- видеть статус заказа: создан, принят, готовится, в доставке, завершен или отменен.

Смысл функции: клиент понимает, на каком этапе находится заказ, и меньше обращается к персоналу вручную.

### 3.8 Уведомления через Telegram

Клиентский бот должен обеспечивать:

- первичный вход в систему;
- регистрацию по номеру телефона;
- переход в Mini App;
- информирование пользователя о важных изменениях по заказу.

Смысл функции: Telegram используется как канал коммуникации без SMS и сторонних приложений.

## 4. Функциональность администратора ресторана

Административный контур представлен Mini App (`admin_panel`) и ботом администратора (`admin_bot`). Доступ администратора зависит от привязки сотрудника к ресторану и выданных прав.

### 4.1 Вход и список ресторанов

Администратор должен иметь возможность:

- открыть панель из Telegram;
- пройти авторизацию;
- увидеть список ресторанов, к которым он привязан;
- выбрать ресторан для работы.

Смысл функции: один сотрудник может работать с одним или несколькими ресторанами, а доступ определяется на backend.

### 4.2 Управление заказами

Администратор должен иметь возможность:

- видеть список заказов ресторана;
- открывать детали заказа;
- видеть состав заказа, клиента, телефон, комментарий, сумму, тип заказа и адрес или стол;
- менять статус заказа по процессу: `CREATED` -> `ACCEPTED` -> `COOKING` -> `DELIVERY` -> `DONE`;
- отменять заказ при необходимости;
- отмечать заказ как оплаченный;
- печатать кухонный чек для новых или принятых заказов.

Смысл функции: ресторан получает рабочее место для обработки заказов без бумажных журналов и ручной переписки.

### 4.3 Управление меню

Администратор с полным доступом должен иметь возможность:

- добавлять новое блюдо;
- редактировать название, описание, цену, категорию, вес, калорийность и изображение;
- загружать изображения блюд;
- включать и выключать доступность блюда;
- включать и выключать доступность целой категории;
- удалять блюда.

Смысл функции: ресторан самостоятельно поддерживает актуальность меню без участия разработчика или суперадминистратора.

### 4.4 Настройки ресторана

Администратор с полным доступом должен иметь возможность:

- изменить название ресторана;
- изменить адрес или описание местоположения;
- задать время работы для гостей;
- задать отдельное окно приема заказов;
- загрузить обложку ресторана;
- указать Telegram Group Chat ID для уведомлений по заказам.

Смысл функции: ресторан управляет своей публичной карточкой и операционными ограничениями.

### 4.5 Управление сотрудниками

Администратор с полным доступом должен иметь возможность:

- просматривать команду ресторана;
- добавлять сотрудника по Telegram ID;
- добавлять сотрудника по телефону;
- выдавать права доступа;
- удалять сотрудника из ресторана.

В системе используются уровни прав:

| Право | Описание |
|---|---|
| `CAN_LOOK_ORDERS` | Ограниченный доступ: просмотр и обработка заказов |
| `CAN_EDIT_MENU` | Полный доступ: заказы, меню, настройки, сотрудники и аналитика |

Смысл функции: владелец или управляющий может разделить доступы между кассирами, поварами и ответственными администраторами.

### 4.6 Аналитика ресторана

Администратор с полным доступом должен иметь возможность:

- видеть выручку за выбранный период;
- видеть количество заказов;
- видеть средний чек;
- сравнивать доставку и заказы в зале;
- видеть оплаченные и неоплаченные заказы;
- смотреть динамику выручки по дням;
- анализировать заказы за текущий день.

Смысл функции: ресторан получает базовую управленческую аналитику для контроля продаж и операционной нагрузки.

### 4.7 Уведомления администратора

Бот администратора должен обеспечивать:

- быстрый переход в панель ресторана;
- получение событий о новых заказах;
- связь с backend через внутренний секрет для безопасной обработки служебных действий.

Смысл функции: сотрудники быстрее узнают о новых заказах и не пропускают их в рабочем процессе.

## 5. Функциональность суперадминистратора

Суперадминский контур представлен панелью (`superadmin_panel`) и ботом суперадминистратора (`superadmin_bot`). Доступ ограничивается списком разрешенных Telegram ID.

### 5.1 Управление ресторанами

Суперадминистратор должен иметь возможность:

- просматривать все рестораны платформы;
- искать ресторан по ID, названию или адресу;
- создавать новый ресторан;
- назначать владельца ресторана;
- видеть количество сотрудников, блюд и заказов;
- включать или отключать ресторан;
- удалять ресторан, если это допустимо по бизнес-правилам;
- сбрасывать аналитические данные ресторана при необходимости.

Смысл функции: суперадминистратор управляет подключением заведений к платформе и контролирует их состояние.

### 5.2 Управление пользователями

Суперадминистратор должен иметь возможность:

- просматривать список пользователей;
- искать пользователей по ID, username, телефону или email;
- открывать карточку пользователя;
- видеть телефон, адрес, курьерский статус, привязки к ресторанам и количество заказов;
- включать или отключать пользователя;
- удалять пользователя, если это допустимо по ограничениям данных.

Смысл функции: платформа может контролировать доступ пользователей и решать спорные или технические ситуации.

### 5.3 Глобальный контроль заказов

Суперадминистратор должен иметь возможность:

- видеть заказы по всей платформе;
- искать заказ по номеру, ресторану или пользователю;
- открывать детальную карточку заказа;
- видеть состав заказа, сумму, клиента, ресторан, тип заказа, адрес или стол и статус.

Смысл функции: суперадминистратор может разбирать проблемные заказы и контролировать работу платформы в целом.

### 5.4 Сводная аналитика

Суперадминистратор должен иметь возможность:

- видеть общее количество пользователей;
- видеть общее количество ресторанов;
- видеть общее количество заказов;
- использовать эти показатели для оценки активности платформы.

Смысл функции: базовая сводка показывает масштаб использования системы и динамику развития проекта.

### 5.5 Технические инструменты

Суперадминистратор должен иметь возможность:

- проверять состояние backend через `/health`;
- видеть напоминания по критически важным секретам интеграции;
- использовать команды суперадмин-бота для проверки состояния, статистики, заказа, ресторана или пользователя.

Смысл функции: платформа получает минимальный эксплуатационный контур для контроля доступности системы.

## 6. Дополнительные контуры

### 6.1 Курьерский контур

Курьер должен иметь возможность:

- видеть назначенные заказы на доставку;
- видеть активные доставки;
- просматривать историю доставок;
- получать данные, необходимые для передачи заказа клиенту.

Смысл функции: доставка внутри ограниченной территории становится управляемой и отслеживаемой.

### 6.2 Контур поддержки

Оператор поддержки должен иметь возможность:

- получать обращения пользователей через Telegram;
- создавать тикеты поддержки;
- закрывать обработанные обращения;
- связывать обращение с пользователем или проблемным заказом.

Смысл функции: спорные ситуации и ошибки не теряются в личных чатах и могут обрабатываться централизованно.

## 8. Необходимые улучшения, которые стоит добавить

Ниже перечислены функции, которые логично добавить для повышения качества проекта и усиления дипломной работы.

### 8.1 Для клиентской стороны

1. **Онлайн-оплата.** Добавить оплату картой или через Telegram Payments, чтобы уменьшить ручной контроль оплаты.
2. **Повтор заказа.** Дать клиенту кнопку "Повторить заказ" из истории.
3. **Избранные рестораны и блюда.** Позволить сохранять часто используемые позиции.
4. **Оценка заказа.** Добавить рейтинг и комментарий после завершения заказа.
5. **Push-уведомления о статусах.** Расширить уведомления: заказ принят, готовится, передан в доставку, завершен.
6. **Промокоды и скидки.** Добавить механизм акций для повышения лояльности.
7. **Поиск по меню.** Добавить быстрый поиск блюд по названию.

### 8.2 Для администратора ресторана

1. **Звуковое уведомление о новом заказе.** Это снизит риск пропустить заказ в активной смене.
2. **Очередь заказов по кухне.** Отдельный kitchen display с крупными карточками заказов для поваров.
3. **Причина отмены заказа.** При отмене фиксировать причину: нет блюда, ошибка клиента, закрыт ресторан и т.д.
4. **Стоп-лист.** Быстро отключать блюда на день без удаления из меню.
5. **Смены сотрудников.** Фиксировать, кто обработал заказ и в какую смену.
6. **Экспорт отчетов.** Выгружать заказы и выручку в Excel/CSV.
7. **Гибкая настройка прав.** Разделить права более детально: заказы, меню, сотрудники, аналитика, настройки.

### 8.3 Для суперадминистратора

1. **Аудит действий.** Логировать важные действия: кто создал ресторан, изменил статус, удалил пользователя или блюдо.
2. **Расширенная аналитика платформы.** Добавить GMV, выручку по ресторанам, конверсию заказов, популярные блюда.
3. **Мониторинг ошибок.** Показывать ошибки backend, ботов и панелей в отдельном разделе.
4. **Управление ролями суперадминов.** Добавить не только allowlist ID, но и роли: владелец платформы, оператор, техподдержка.
5. **Модерация ресторанов.** Вводить статус подключения: заявка, проверка, активен, заблокирован.
6. **Резервное копирование данных.** Добавить контроль последних backup и восстановление из резервной копии.
7. **Централизованная рассылка.** Отправлять важные сообщения ресторанам или пользователям через Telegram.

### 8.4 Для надежности и эксплуатации

1. **Автоматизированные тесты.** Покрыть checkout, смену статусов, права сотрудников и суперадминские операции.
2. **Очередь событий.** Вынести уведомления в очередь, чтобы сбой Telegram не ломал оформление заказа.
3. **Логи и трассировка.** Хранить структурированные логи для поиска ошибок в заказах.
4. **Rate limiting.** Ограничить частоту запросов к публичным endpoint, чтобы защитить API.
5. **Резервные сценарии уведомлений.** Если бот недоступен, сохранять событие и повторять отправку позже.
6. **Политика хранения персональных данных.** Формализовать удаление, обезличивание и сроки хранения данных.

| Средний | Повтор заказа, стоп-лист, экспорт отчетов, мониторинг ошибок, поиск по меню |
| Низкий | Избранное, промокоды, централизованная рассылка, расширенная ролевая модель |

Для дипломного проекта наиболее важно подчеркнуть функции с высоким приоритетом, потому что они напрямую влияют на надежность, безопасность, прозрачность обработки заказов и практическую применимость системы.
