# KULCHA Thesis README — база для ВКР

Документ подготовлен как практическая основа для написания выпускной квалификационной работы (ВКР) по теме цифровизации процессов общественного питания с использованием Telegram-экосистемы и веб-технологий.

## 1. Паспорт проекта

### 1.1 Тема и предметная область

**KULCHA** — программная платформа приема и сопровождения заказов для кафе и небольших ресторанов.  
Система объединяет:

- клиентский контур (Telegram Mini App + пользовательский бот);
- контур персонала ресторана (Mini App + бот администратора);
- контур платформы (панель суперадминистратора + бот суперадминистратора);
- серверную часть с REST API и единой базой данных.

### 1.2 Цель разработки

Повысить скорость и прозрачность обработки заказов в малом общепите за счет единой цифровой среды, интегрированной с Telegram.

### 1.3 Задачи, решаемые системой

1. Предоставить клиенту удобный канал заказа (каталог, меню, корзина, оформление).
2. Автоматизировать работу ресторанов с заказами и меню.
3. Централизовать управление ресторанами, пользователями и аналитикой на уровне платформы.
4. Обеспечить уведомления и сервисные операции через Telegram-боты.
5. Обеспечить разворачиваемость системы в контейнерной инфраструктуре.

## 2. Актуальная архитектура (фактическая реализация)

> Важно для ВКР: в текущей рабочей реализации используется `backend/` (Python FastAPI), а не `backend_` на Java.

### 2.1 Компонентная схема

```text
Клиентские интерфейсы:
  - user_panel (Telegram Mini App)
  - admin_panel (Telegram Mini App)
  - superadmin_panel (Web/Mini App)

Telegram-боты:
  - user_bot
  - admin_bot
  - superadmin_bot
  - support_bot

Сервер:
  - backend (FastAPI, REST, SQLAlchemy async, Alembic)
  - PostgreSQL
  - Object Storage (S3-compatible)

Инфраструктура:
  - Docker Compose
  - Caddy reverse proxy (домены и TLS)
```

### 2.2 Структура репозитория

| Каталог | Назначение |
|---|---|
| `backend/` | Основной API-сервер на FastAPI, бизнес-логика, ORM-модели, миграции |
| `backend/migrations/` | Миграции Alembic |
| `user_panel/` | Клиентский интерфейс заказа |
| `admin_panel/` | Интерфейс ресторана (заказы, меню, аналитика) |
| `superadmin_panel/` | Панель управления платформой |
| `bots/` | Четыре Telegram-бота на aiogram |
| `deploy/` | Dockerfiles, Caddy, скрипты запуска |
| `scripts/` | Вспомогательные скрипты эксплуатации и миграций |
| `docker-compose.yml` | Полная оркестрация сервисов |

## 4. Ролевой и функциональный контур

### 4.1 Роли пользователей

- **Клиент**: просмотр ресторанов, выбор блюд, оформление заказа, отслеживание статуса.
- **Сотрудник ресторана**: обработка заказов, редактирование меню, просмотр показателей.
- **Курьер**: доступ к заказам на доставку и истории доставки.
- **Суперадминистратор**: управление ресторанами и пользователями, контроль системы.
- **Оператор поддержки**: обработка заявок через support-бота.

### 4.2 Основные пользовательские сценарии

1. Клиент запускает Mini App из Telegram и формирует заказ.
2. Backend валидирует заказ и создает записи `order` + `order_positions`.
3. Администратор ресторана обрабатывает заказ, меняя его статус.
4. Клиент отслеживает статус через интерфейс или бота.
5. Суперадминистратор контролирует агрегированную картину по платформе.

## 5. Серверная часть: структура и логика

### 5.1 Модули backend

- `app/main.py` — инициализация FastAPI и роутеров.
- `app/config.py` — конфигурация через `KULCHA_*` переменные окружения.
- `app/database.py` — подключение к PostgreSQL.
- `app/models/` — ORM-модели предметной области.
- `app/routers/` — REST endpoints (`auth`, `users`, `restaurants`, `meals`, `orders`, `staff`, `admin` и др.).
- `app/services/` — бизнес-сервисы (авторизация Telegram, нотификации, хранилище, проверки доступа).

### 5.2 Ключевые сущности данных

- `User`
- `Restaurant`
- `Meal`
- `Order`
- `OrderPosition`
- `Staff`
- `Courier`
- `RefreshSession`
- `SubscriptionLog`
- `SupportTicket`

Ключевые перечисления:

- `MealCategory`
- `OrderStatus`
- `OrderType`
- `StaffPermission`

### 5.3 REST API (укрупненно)

Префикс: `/api/v1`.

- Аутентификация: `/auth`
- Пользователи: `/users`
- Рестораны: `/restaurants`
- Блюда: `/meals`
- Заказы: `/orders`
- Позиции заказа: `/order-positions`
- Сотрудники и доступы: `/staff`, `/restaurants/{restaurant_id}/staff`
- Курьерский контур: `/couriers`, `/courier-panel`
- Административный контур: `/admin`
- Поддержка (внутренний API): `/internal/support`

### 5.4 Значимые бизнес-правила

1. Заказ валидируется по доступности ресторана и временным ограничениям (часовой пояс MSK).
2. Для части операций требуется проверка внутреннего секрета (`KULCHA_INTERNAL_API_SECRET`).
3. Для бот-запросов может использоваться `KULCHA_BOT_API_SECRET`.
4. Ролевой доступ сотрудников ресторана разделен по правам (`CAN_EDIT_MENU`, `CAN_LOOK_ORDERS`).
5. Суперадмин-контур ограничивается allowlist-идентификаторами Telegram.

## 6. Клиентские приложения

### 6.1 `user_panel` (клиентский Mini App)

Маршруты включают: каталог кафе, меню ресторана, корзину, checkout, профиль, историю заказов.  
Ключевая функция: быстрый заказ через Telegram без отдельного мобильного приложения.

### 6.2 `admin_panel` (Mini App ресторана)

Функции: список "моих" ресторанов, обработка заказов, управление меню, базовая аналитика.  
Привязка сотрудников к ресторанам выполняется через backend-контур прав.

### 6.3 `superadmin_panel`

Функции: управление ресторанами и пользователями, агрегированные данные по заказам, служебные инструменты контроля платформы.

## 7. Telegram-боты

### 7.1 `user_bot`

- первичный контакт с клиентом;
- регистрация через отправку телефона;
- переход в Mini App;
- запрос статуса заказа.

### 7.2 `admin_bot`

- входная точка для сотрудника ресторана;
- переход к панели управления;
- обработка событий по заказам (в связке с backend и внутренним секретом).

### 7.3 `superadmin_bot`

- сервисные команды (`/health`, `/stats`, `/order`, `/restaurant`, `/user`);
- контроль доступа по списку разрешенных Telegram ID.

### 7.4 `support_bot`

- создание и маршрутизация тикетов поддержки;
- интеграция с группой поддержки Telegram;
- взаимодействие с внутренним API backend.

## 8. Безопасность и управление доступом

1. Конфиденциальные параметры вынесены в переменные окружения.
2. Для межсервисных вызовов используются отдельные shared secrets.
3. Реализован контур `access/refresh` сессионной авторизации.
4. Ограничение доступа суперадминов задается конфигурационно (`KULCHA_SUPERADMIN_ALLOWED_IDS`).
5. Для прод-окружения предусмотрен HTTPS через Caddy.

## 9. Развертывание и эксплуатация

### 9.1 Локальный запуск backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Проверка: `GET http://localhost:8000/health`.

### 9.2 Полный запуск в контейнерах

```bash
docker compose up -d
```

Поднимаются БД, backend, панели, боты и Caddy-шлюз.

### 9.3 Критически важные переменные

- База данных: `POSTGRES_*`, `KULCHA_DATABASE_URL`
- Токены ботов: `KULCHA_*_BOT_TOKEN`
- Секреты интеграции: `KULCHA_INTERNAL_API_SECRET`, `KULCHA_BOT_API_SECRET`
- Объектное хранилище: `KULCHA_OBJECT_STORAGE_*`
- Домены и публичный API: `API_DOMAIN`, `PUBLIC_API_URL`, `KULCHA_CORS_ALLOWED_ORIGINS`

## 10. Тестирование (для раздела ВКР)

На текущем этапе в репозитории отсутствует полноценный автотестовый контур (pytest/vitest).  
Рекомендуется зафиксировать в пояснительной записке:

1. **Модульное тестирование (планируемое):** сервисы валидации заказа и авторизации.
2. **Интеграционное тестирование:** API-цепочка "создание заказа -> позиции -> смена статуса".
3. **Системное тестирование:** сценарии клиент/админ/суперадмин/боты.
4. **Нагрузочная оценка (базовая):** рост числа заказов и время ответа API.

## 11. Научно-практическая новизна и значимость

Для текста ВКР можно формулировать следующие акценты:

- единый цифровой контур для всех участников процесса заказа;
- снижение операционных задержек за счет Telegram-first подхода;
- унификация управления контентом (меню, статусы, роли) в одном backend;
- применимость решения для малого и среднего ресторанного бизнеса.

## 12. Ограничения текущей реализации

1. Недостаточное покрытие автотестами.
2. Часть аналитики формируется на клиентской стороне.
3. Требуется дальнейшее усиление ролевой модели и аудита действий.
4. Нужна формализация SLA и централизованный мониторинг метрик.

## 13. Перспективы развития

1. Выделенный аналитический модуль (предрассчитанные витрины KPI).
2. Расширенная система уведомлений (event-driven, очередь сообщений).
3. Продвинутое управление персоналом ресторана и графиком смен.
4. Финансовая отчетность и экспорт в учетные системы.
5. Формирование полноценного набора автоматизированных тестов.
